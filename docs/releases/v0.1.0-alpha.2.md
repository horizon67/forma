# Forma v0.1.0-alpha.2

This second public alpha makes repeat generation an explicit, reviewable update
workflow. It is an intentionally unstable pre-release, not a stable
compatibility or generated-code correctness guarantee.

## Included

- Baseline-aware `generate`: full generation for a fresh target, bounded
  incremental updates for semantic or Implementation Manifest changes, and
  no-op without starting or authenticating an AI when neither changes (#4).
- Automatic per-worktree generation history, so normal repeat commands do not
  require `--previous` or a full/update/no-op mode flag. Failed or interrupted
  attempts preserve the previous baseline and stop for deliberate recovery (#5).
- Provider-independent execution and progress, with a Codex adapter as the
  first real backend. Default line-oriented progress, configurable heartbeats,
  `--verbose`, and `--progress=json` expose only fixed event categories (#6).
- Ctrl+C/SIGTERM process-group cancellation, bounded final Git/history cleanup,
  and distinct completed, no-op, failed, cancelled, and timed-out results.
- macOS and Linux binaries for amd64 and arm64, plus `SHA256SUMS`.

The [alpha language profile](https://github.com/horizon67/forma/blob/v0.1.0-alpha.2/docs/alpha-language-profile.md)
retains alpha.1's accepted `.forma` semantics and Implementation Manifest schema.
Generation Request output advances from `v0alpha4` to `v0alpha5` for policy change
metadata. Alpha.1 Requests remain readable with their original canonical bytes
and lineage; alpha.1 binaries cannot read the new Request format. History and
progress each use an independent `v0alpha1` schema, not language semantics.

## Install and upgrade

```sh
go install github.com/horizon67/forma/cmd/forma@v0.1.0-alpha.2
forma version
```

The expected version is `forma v0.1.0-alpha.2`. Check PATH if another version
runs. Prebuilt binary and checksum instructions are in the
[installation guide](https://github.com/horizon67/forma/blob/v0.1.0-alpha.2/docs/install.md).

Installing alpha.2 does not create history for an alpha.1-generated application.
Preserve the exact original Generation Request. Review the existing implementation
against that Request, then use `generate --previous <original-request.json>`
once to adopt it. With unchanged meaning this imports a baseline without an AI
run; with changed meaning it performs the corresponding bounded update. Normal
subsequent commands select their baseline automatically.

Do not manufacture a baseline from today's changed specification and assume the
existing application satisfies it. An unchanged explicit import does not
generate missing code. If the original Request is unavailable, assess adoption
explicitly or generate into a fresh isolated target instead. History is local
Git metadata: cloning, moving, switching branches, or failed runs may require
the documented [adoption/recovery workflow](https://github.com/horizon67/forma/blob/v0.1.0-alpha.2/docs/generation-history.md).
It is never verification evidence or a rollback facility.

## AI and review boundary

Only Codex CLI is connected in alpha.2, with separate user authentication.
Other live providers, provider selection, and new authentication integrations
remain future work. The common backend interface does not depend on Codex CLI
types or OS processes. Display options and backend identity do not change
Generation Requests or trigger regeneration by themselves.

The Codex adapter uses structured events and a separate bounded private summary
file. Progress never publishes raw AI text, commands, tool output, reasoning,
credentials, or raw stderr, including in verbose mode. The final AI summary is
separate, explicitly unverified free text and may contain sensitive information.

Forma does not execute the generated application's build/tests on the host.
After generation, review the diff and run the reviewed repository commands.
Incremental edit scope is an instruction to the agent, not a mechanical proof
that every change was related. No-op is not an audit or successful test result.
Cancellation is not rollback: review partial mutations before recovery/retry.

## Qualification and known limitations

The release gate runs tests, race checks, vet, deterministic compiler probes,
repository E2E targets, clean source installation, and four-platform archive
builds. Tagged installation is additionally checked on macOS and Linux before
GitHub publishes assets. Fake backends, clocks, structured streams, real PTYs,
and real SIGINT/SIGTERM tests exercise the generation orchestration without a
live AI service.

- The specific signup npm-to-Bun migration in #3 still needs live application
  validation; orchestration tests are not evidence that this migration built
  or that its application tests passed.
- No new live Codex compatibility matrix is claimed. The earlier alpha.1
  dogfood observation (`codex-cli 0.144.4`) is historical evidence, not alpha.2
  qualification of every CLI version or provider account.
- Policy removals/ID replacements and unsupported semantic removals fail
  closed. Repair and audit are not automatic generation modes.
- Use only a user-owned, trusted worktree. Windows, hostile-repository
  containment, stable compatibility guarantees, and the unimplemented language
  constructs listed in the alpha profile remain outside this release.
- Human Review Requirements remain open until reviewed; neither agent
  completion nor local history marks them verified.
